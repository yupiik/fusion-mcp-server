Design

This page is for contributors, and for anyone wanting to know what happens between an HTTP request and a tool call.

Principle

MCP is JSON-RPC 2.0. Fusion already generates a complete JSON-RPC stack at build time, so the implementation is mostly wiring rather than protocol code:

  • the MCP methods are plain @JsonRpc methods (MCPJSONRPCProtocol) registered in the same registry as the application ones,

  • tools/call re-enters JsonRpcHandler, so a tool invocation follows the exact same code path as a direct JSON-RPC call - binding, validation, error mapping included,

  • the descriptors come from the OpenRPC document the annotation processor writes in META-INF/fusion/jsonrpc/openrpc.json,

  • only the transport is specific: sessions, SSE, headers, and the routing of client responses.

A tool call, step by step

POST /mcp  {"method":"tools/call","params":{"name":"my/tool","arguments":{...}}}
 |
 |-- MCPEndpoint                     read the body once, split requests / notifications / client responses
 |     validate MCP-Protocol-Version -> 400 if unsupported
 |     resolve Mcp-Session-Id        -> 404 if unknown, create it when the call is initialize
 |     bind the session on the request attribute
 |
 |-- JsonRpcHandler.execute          the standard Fusion dispatch
 |     |
 |     |-- MCPJSONRPCProtocol#callTool
 |           descriptors.isTool(name)  -> -32602 when it is not an @MCPTool method
 |           handler.execute({method: name, params: arguments})   nested, same stack
 |             |
 |             |-- the application method, bound and invoked by generated code
 |           map the result: ToolResponse as is, else structuredContent + text block
 |           map a failure: isError = true, unless the error code is a reserved JSON-RPC one
 |
 |-- MCPEndpoint                     write the JSON-RPC response (200), or 202 when there is nothing to answer

Decisions worth knowing

Own the POST endpoint. The Fusion JSON-RPC endpoint cannot express the MCP transport: session headers with their 400/404 semantics, 202 for notifications, and above all the client responses - a JSON-RPC message without method, which the standard validation rejects. MCPEndpoint is therefore registered with @Order(900), before the Fusion one (1000), and delegates all the JSON-RPC work to the same handler. Bean lookups are sorted by ascending priority and the first matching endpoint wins, which makes the precedence deterministic.

Descriptors computed once, at startup. Tools and prompts are known at build time, so tools/list is a constant. It also means tools/list never runs user code and cannot fail.

An allow list for tools/call. Without it, tools/call would reach every JSON-RPC method of the application - and the MCP protocol methods themselves. Only mcp.type=tool methods are callable.

Tool failures are results. The specification wants an execution failure inside the result (isError: true) so the model can read and react to it; only an invalid call is a JSON-RPC error. The frontier used here is the reserved code range (-32700, -32600..-32603).

Merge all the OpenRPC documents. There is one per module using the processor - one for this library, one for the application - so reading a single classpath resource would drop the methods of every other module depending on the classpath order.

Resources through a SPI, tools through annotations. Tools and prompts are code, known at build time; resources are data, discovered at runtime. Hence @MCPTool/@MCPPrompt on one side and the MCPResources bean on the other.

Buffer the server to client messages. A tool can send a request before the client opens its stream, and a client can reconnect. SseBus therefore queues frames, respects the subscriber demand and keeps a replay window of 128 messages for Last-Event-ID.

Notes on the wire model

Every MCP structure is a @JsonModel record in model, so its codec is generated - no reflection, GraalVM friendly. Naming follows the specification: XxxResponse is a JSON-RPC result, XxxParameters a params, XxxNotification the params of a notification. Two pairs are easy to confuse and deliberately named after the specification: Resource (descriptor) versus ResourceContents (payload), and Capabilities (the client ones, in initialize params) versus InitializeResponse.Capabilities (the server ones).

Optionality is expressed the JSON-Schema way. The Fusion OpenRPC document flags each schema with nullable, MCP needs a required list on the enclosing object, and DescriptorService does that translation.

Known limitations

  • sessions live in memory: a clustered deployment needs sticky routing on the Mcp-Session-Id header,

  • a tool returning Optional<T> has no usable outputSchema - and does not serialize either, Fusion has no Optional JSON codec - so return T or a CompletionStage<T>,

  • Fusion >= 1.0.38 is required: earlier releases describe an asynchronous result as a map of T in the generated OpenRPC document, which would make the outputSchema of every asynchronous tool wrong.

JSON-RPC reference of the protocol methods

The MCP methods are plain @JsonRpc methods, so they end up in the OpenRPC document of the library like any other - this section is generated from it and therefore always matches what is deployed.

Methods

completion/complete

Parameter structure: either.

Suggests values for a prompt argument or a resource template variable.

Parameters:

  • argument ( CompletionArgument ): The argument being completed and its current value.

  • context ( CompletionContext ): The arguments already resolved.

  • ref ( CompletionRef ): What is completed: a prompt or a resource template.

Result: CompleteResult

initialize

Parameter structure: either.

Negotiates the protocol version and returns the server capabilities.

Parameters:

  • protocolVersion (string): The protocol version the client wants to use.

  • capabilities ( Capabilities ): What the client supports: roots, sampling, elicitation.

  • clientInfo ( ClientInfo ): Which client is connecting.

Result: InitializeResponse

logging/setLevel

Parameter structure: either.

Sets the minimum severity of the log records sent to the client.

Parameters:

  • level (string): A syslog level name: debug, info, notice, warning, error, critical, alert or emergency.

Result: object

notifications/cancelled

Parameter structure: either.

The client gave up on a request it sent.

Parameters:

  • reason (string): Why the request was cancelled.

  • requestId (object): The cancelled request id, a string or a number.

Result: null

notifications/initialized

Parameter structure: either.

The client is ready, the session can be used.

Parameters:

  • _meta ( Metadata )

Result: null

notifications/progress

Parameter structure: either.

Progress of a request the client sent to the server.

Parameters:

  • message (string)

  • progress (number)

  • progressToken (object)

  • total (number)

Result: null

notifications/roots/list_changed

Parameter structure: either.

The client filesystem roots changed.

Parameters:

  • _meta ( Metadata )

Result: null

ping

Parameter structure: either.

Liveness check, see https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/ping .

Parameters:

  • _meta ( Metadata )

Result: object

prompts/get

Parameter structure: either.

Expands a prompt template.

Parameters:

  • name (string): The prompt name, as returned by prompts/list.

  • arguments (object): The prompt arguments, all strings.

  • inputResponses (object): The answers to a previous input_required request, as top-level params.

  • requestState (string): The token to resume a previous input_required interaction.

  • _meta (object)

Result: MCPResult

prompts/list

Parameter structure: either.

Lists the prompt templates the user can pick.

Parameters:

  • cursor (string): Pagination cursor, unused: all the prompts are returned at once.

Result: ListPromptsResponse

resources/list

Parameter structure: either.

Lists the resources the client can read.

Parameters:

  • cursor (string): Pagination cursor, unused: all the resources are returned at once.

Result: ListResourcesResponse

resources/read

Parameter structure: either.

Reads the contents of a resource.

Parameters:

  • uri (string): The resource uri.

  • _meta (object)

Result: MCPResult

resources/subscribe

Parameter structure: either.

Asks to be notified when a resource changes.

Parameters:

  • uri (string): The resource uri to watch.

Result: object

resources/templates/list

Parameter structure: either.

Lists the parameterized resources the client can read.

Parameters:

  • cursor (string): Pagination cursor, unused: all the templates are returned at once.

Result: ListResourceTemplatesResponse

resources/unsubscribe

Parameter structure: either.

Stops watching a resource.

Parameters:

  • uri (string): The resource uri to stop watching.

Result: object

server/discover

Parameter structure: either.

What this server supports over the stateless protocol, it replaces initialize for the stateless clients - no session is created.

Parameters:

  • _meta ( MCPRequestMetadata )

Result: ServerDiscoverResponse

subscriptions/cancel

Parameter structure: either.

Closes the server to client stream opened by subscriptions/listen.

Parameters:

  • _meta (object)

Result: object

subscriptions/listen

Parameter structure: either.

Opens the server to client stream of the stateless protocol, it stays open until the client calls subscriptions/cancel.

Parameters:

  • notifications ( SubscriptionFilter )

  • _meta (object)

Result: object

tasks/cancel

Parameter structure: either.

Signals the cancellation of a long-running task; cancellation is cooperative.

Parameters:

  • taskId (string): The task identifier.

Result: object

tasks/get

Parameter structure: either.

Polls the current state of a long-running task of the tasks extension.

Parameters:

  • taskId (string): The task identifier.

Result: Task

tasks/list

Parameter structure: either.

Lists the live long-running tasks of the tasks extension.

Parameters:

  • cursor (string): Pagination cursor, unused: all the tasks are returned at once.

Result: ListTasksResponse

tasks/update

Parameter structure: either.

Answers the input requests a task is blocked on, acknowledged with an empty result.

Parameters:

  • taskId (string): The task identifier.

  • inputResponses (object): The answers to the task outstanding input requests.

Result: object

tools/call

Parameter structure: either.

Calls a tool.

Parameters:

  • name (string): The tool name, as returned by tools/list.

  • arguments (object): The tool arguments, they must match its inputSchema.

  • inputResponses (object): The responses to a previous input_required request, as top-level params.

  • requestState (string): The token to resume a previous input_required interaction.

  • _meta (object)

Result: MCPResult

tools/list

Parameter structure: either.

Lists the tools the model can call.

Parameters:

  • cursor (string): Pagination cursor, unused: all the tools are returned at once.

Result: ListToolsResponse
